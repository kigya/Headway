Add a `FreudSearchBar` component to the design system. This is a search field that visually looks like a pill with a placeholder and a magnifying-glass icon on the right, and it should behave the same in Compose Multiplatform on Android, iOS, Web, and Desktop. The component must be width-adaptive: on mobile it fills the container width and matches the mockups, while on web/desktop at large widths it must not stretch its internals oddly (text must not drift, the icon must stay on the right edge, padding and height must remain consistent). By default the component should not impose a fixed size; it should respect `modifier` so screens can use `fillMaxWidth()`, constrain max width, and so on.

Content-wise, the component accepts a `placeholder` string and shows it when the field is empty. The current text value must be observable from outside: either via a controlled API (`value` + `onValueChange`) or via an explicit callback that reports every text change. It must be easy for consumers to know the current text at any moment and store it in their own state without reaching into the component.

A key part is debounce and the correct moment when it is time to search. The component must support a delay before emitting a search event: the user types, the component updates text immediately, but the "search signal" should fire only after a pause (debounce), so search is not triggered on every keystroke. The debounce interval must be configurable with a sensible default (for example 300–500 ms). Distinguish two events: (1) text change (frequent), (2) readiness to perform search (rare, after debounce). The component should expose separate callbacks: one for `onTextChanged` (or `onValueChange`), and another for `onSearchTriggered` (or `onDebouncedQueryChanged`) that fires only when debounce has settled.

Also clarify how the client is notified that a request may be made now. The component should not only emit debounced text but provide clear semantics: "this is the moment when the user finished typing and search can start." The second callback should fire exactly when the debounce window ends, and clients should treat it as the trigger to run search. In addition, support an explicit manual search trigger (for example keyboard Search/Enter) so desktop/web and mobile IME behave as expected. Even without a manual trigger, the debounce callback should be enough to avoid searching every second.

The magnifying-glass icon on the right should have a light animation (pulse) while debounce is running and we wait for input to stabilize, or when debounce completes and we signal that search can run. Pick one clear semantics to avoid visual noise: for example, as soon as the user types a character, start the debounce timer and begin a soft pulse on the icon; when debounce expires, do one short accent (or stop pulsing) and call `onSearchTriggered(query)`. The animation must be lightweight, not resource-heavy, not laggy on web/desktop, and consistent across platforms.

Implementation and API: no slot lambdas for the icon or "right-side content" — the magnifying-glass icon is always the same and always in the same place. Colors, typography, corner radius, and height must come strictly from design-system tokens, with no raw values in the public API. Keep extra parameters minimal: placeholder, current value/change callback, debounce duration, and the "search trigger" callback. Optionally add `isEnabled` and `isReadOnly` only if they are truly needed in the product.

In previews, show: light/dark theme, empty field with placeholder, filled field, long text (to verify clipping/scrolling behavior), and a demo of debounce behavior and pulsing (in preview you can simulate input and state changes via a timer, similar to `FreudIconPreview` / `FreudButtonPreview`). Also show a wide scene (web/desktop) where the component is constrained to max width and centered, so adaptive layout is visible rather than "stretched to 1400px".
