Add a `FreudHomeHeader` component to the design system. It is the top header of the home screen and must work the same in Compose Multiplatform on Android, iOS, Web, and Desktop. It renders as a standalone block at the top of the screen and must adapt to different widths: on phones use a compact layout (as in mobile mockups); on web/desktop at large widths it must not break or stretch elements oddly — either constrain content to a reasonable max width inside, or rearrange so the greeting/avatar block stays on the left and the date and extra metrics stay on the right, all remaining tidy and readable. The component must be adaptive not only by width but also by density/scale, and look consistently "design-system native" on all platforms without platform artifacts.

The header always includes the user avatar, greeting, and current date. The avatar accepts a URL and renders from that URL; a border around the image is not needed and must not be part of the default look (stroke on Figma was for demonstration). To avoid baking custom image loading into `FreudHomeHeader`, use `FreudAsyncImage`, which loads the image, shows a placeholder while loading, and handles errors (for example a fallback icon/placeholder). `FreudHomeHeader` must use this DS component, not external implementations, so behavior is identical on all four targets. Avatar size and shape (circle/rounded rect) must be fixed by the design system (tokens), with no external customization.

The greeting accepts the user name (string) and is always formatted as "Hi, <Name>!" (or a localizable equivalent; from the component's perspective an input name and final greeting string are enough). The date in the header is always shown, taken as "today" and formatted consistently on all platforms (avoid different defaults on iOS/Android/Web). Prefer accepting a preformatted date string or a locale-aware formatter/provider, while keeping screen usage simple so callers do not need heavy boilerplate each time.

The header also has a label for the user role. The role is strictly one of four values: `developer`, `manager`, `mentor`, `employee`. The component must accept the role in a type-safe way (enum/sealed), and show the correct caption/badge and, if needed, a small icon per role. Two additional parameters — `totalReadiness` and `nextSessionType` — are shown only for `mentor` and `employee` roles. For `developer` and `manager` these blocks must not exist in the UI at all: they must not take space and must not be empty placeholders. `totalReadiness` is a progress percentage/number (for example 80%/100%), and its display must handle different values (0, 100, one/two/three digits, etc.). `nextSessionType` is the type of the next session (strictly typed), rendered nearby as a small badge/label; keep the type as enum/sealed so it can grow without breaking the API.

Plan a pleasant loading experience when the screen opens: the header must not pop in abruptly, especially while the avatar is still loading. Prefer user-friendly animations: smooth content appearance (fade/slide) and a neat loading state for the avatar (for example a soft placeholder with crossfade to the image). Animations should be lightweight, work the same on all platforms, and not require extra screen logic — the screen simply renders `FreudHomeHeader`, and initial render / loading / loaded behavior lives inside the component.

For the public API, follow design-system rules: no raw colors/sizes; anything configurable uses tokens. Keep configuration minimal: only what the mockups require (data and a few semantic parameters); layout details, padding, shapes, and typography stay inside the component and stay consistent with other DS components.
